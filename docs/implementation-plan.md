# Kaizen Cross-Check — Implementation Plan (Week 1 vertical slice)

> **For agentic workers:** execute task-by-task with TDD (superpowers:executing-plans or
> subagent-driven-development). Steps use checkbox syntax for tracking.

**Goal:** From a clean checkout, one command processes a folder of synthetic SKU document sets
(JDE-style BOM + product label), runs the BOM ↔ Label check through the deterministic match
ladder, and produces a traceable Excel report plus measured accuracy against ground truth.

**Architecture:** A `src/kaizen` Python package with independent layers: `models` (typed canonical
data), `ingest` (parsers + grouping), `terminology` (explicit relationship store), `matching`
(normalisation, staged ladder, assignment), `checks` (BOM ↔ Label), `reporting` (Excel),
`evaluation` (golden harness), `datasets` (synthetic generator), `cli`. No LLM, no network, no UI.

**Tech stack:** Python 3.13 (3.12 not installed on this machine; nothing 3.13-specific is used),
pydantic v2, PyMuPDF (text + word bounding boxes + annotations + synthetic PDF generation),
openpyxl, rapidfuzz, typer + rich (CLI), pytest.

**Spec:** `docs/problem-understanding.md` (sections 3, 4, 7) and the brief
`docs/reference/hackathon-problem-statement.pdf` (slides 6, 7, 10, 11).

## Global constraints

- Deterministic core: identical inputs + identical terminology produce identical outputs.
- Every `CheckResult` carries a human-readable `explanation` and both source `DocumentItem`s with `Evidence`.
- No classification without a reason; no discrepancy without type, severity, detail.
- Non-physical / zero-qty / inactive BOM lines are never reported as missing from the label.
- Fuzzy matching yields POTENTIAL at best, never EXACT/EQUIVALENT.
- Every run records SHA-256 of inputs, tool + parser versions, thresholds, terminology snapshot hash.
- Nothing hard-coded to specific SKUs; synthetic data is generated by a documented generator.
- Unimplemented capabilities are labelled NOT IMPLEMENTED or PLANNED in code, docs, and report.

## 2. Architecture decision

**Chosen:** single Python package, layered, CLI-first, file in → Excel out (proposal §7, approach A).

Points examined critically before building:

| Concern | Decision |
|---|---|
| Fuzzy over-matching on near-identical descriptions (`GAUZE 10 CM X 10 CM` vs `GAUZE 5 CM X 5 CM`) | Numeric-token guard: disagreeing numeric/dimension tokens block POTENTIAL and yield AMBIGUOUS; ambiguity delta between top-2 candidates also yields AMBIGUOUS. |
| Label multi-column text | Word-bbox based column detection anchored on `N Each -` line starts; continuation lines merged per column. Naive newline splitting is explicitly avoided. |
| BOM print column parsing | Header-word x-positions define column bands; rows grouped by y. Excel/CSV BOM export supported by header-name detection. |
| Redlines | PDF FreeText/StrikeOut annotations overlapping a row are captured into `attributes.redlines`. Hand-drawn/scanned redlines: NOT IMPLEMENTED (documented). |
| Pair/per idioms in label quantities | Captured as `sub_quantity`; a qty difference explainable by the idiom becomes POTENTIAL (needs validation) rather than MISMATCH. |
| Relationship scope | `global` / `family:<prefix>` / `sku:<code>`; item anchors bind a relationship to a BOM item number. Family = leading digits of a SKU code (`1295108NS` → `1295108`). |
| Assignment | Greedy one-to-one by (level rank, score) with conflict detection; Hungarian unnecessary at ≤ 60 lines per SKU. |
| CLI framework | typer + rich; no other runtime deps. |

## 4. Week 1 scope (P0) — tasks in execution order

Each task: write failing tests → run → implement → run → (commit when the user asks for commits).

1. **Project skeleton** — `pyproject.toml`, package init, `python -m kaizen --help`, pytest runs.
2. **Canonical models** — all enums and pydantic models; validation tests (qty Decimal, confidence 0–1, evidence required).
3. **Normalisation** — `normalize(text) -> NormalizedText{raw, normalized, tokens, sorted_key, numeric_tokens}`; table-driven tests (™/®, `W/`, units, plurals, token order, dimension tokens preserved).
4. **Quantity parsing** — `parse_label_line("10 Each - Gauze, 10 cm x 10 cm (4 in. x 4 in.)")` → qty 10, uom EACH, description, sub_quantity None; `(3 per)`, `(1 pair)` → SubQuantity.
5. **BOM categorisation** — `categorize(item_number, description, quantity, flags) -> (ItemCategory, reason)`; rule file; tests for every category incl. qty-0 and inactive.
6. **PDF word utilities** — words with bboxes, line grouping by y, column band assignment, annotation capture; fixture PDFs generated in tests.
7. **Synthetic BOM PDF renderer** (needed by parser tests) — renders header block + column header + rows in the R30460 layout; optional FreeText annotation.
8. **BOM PDF parser** — header fields, rows, categories, `is_active` from Effective Thru, evidence per row; tests on rendered fixtures incl. multi-page.
9. **BOM table parser** — XLSX/CSV export with header detection; same `Document` output; tests.
10. **Synthetic label PDF renderer** — two columns, wrapped lines, ™ symbols, peel-off sub-labels repeating REF, trademark paragraph, LOT/barcode text.
11. **Label parser** — REF (most frequent `REF` token), product name, kit-contents lines with per-line bbox and confidence; tests: wrapped lines merge, columns don't interleave, peel-off REF not treated as content.
12. **Detection + grouping + hashing** — `detect_doc_type(path)`, `group_by_sku(documents) -> list[SkuGroup]` with coverage warnings.
13. **Relationship store** — JSON load/save, `lookup(a_norm, b_norm, ctx)`, scope filtering, item anchors, `snapshot()` hash; default relationships file; tests.
14. **Fuzzy + numeric guard** — `similarity(a, b) -> FuzzyScore{score, numeric_conflict}`; tests for the gauze case.
15. **Match ladder** — staged matchers, `MatchOutcome` with level, score, reason, relationship_id; tests for each level and for "fuzzy never returns EXACT".
16. **Assignment** — candidate matrix, greedy one-to-one, `AMBIGUOUS` when top-2 within delta or label line contested; tests.
17. **Quantity comparison** — `compare_quantities(bom_item, label_item) -> QtyVerdict{equal, explainable_by_idiom, detail}`.
18. **BOM ↔ Label check** — assembles `CheckResult`s incl. REF/parent row, MISSING both directions, LOW_EXTRACTION_CONFIDENCE; requires-validation rule; row IDs `R-<sku>-<seq>`; tests on hand-built documents for every taxonomy type.
19. **Pipeline** — `run_folder(path, store, thresholds) -> Run`; JSON serialisation of `Run`.
20. **Excel report** — sheets/columns as specified in the kickoff §15; conditional fills; decision dropdown; tests open the workbook and assert sheets, headers, a row's values, metadata hashes.
21. **Ground truth + harness** — schema, loader, matching of predicted vs expected rows, metrics (pairing, classification, discrepancy P/R overall and per type, per SKU), console + JSON output.
22. **Dataset builder** — catalog + 10 SKU scenarios covering the 14 required cases; writes PDFs, 2 XLSX BOMs, ground truth, `SCENARIOS.md`; deterministic.
23. **CLI** — `kaizen run <folder> --out <dir>`, `ingest`, `check`, `report`, `eval`, `dataset build`; integration test executes `run` and `eval` on `datasets/golden`.
24. **Tuning + adversarial pass** — run eval, fix false positives/negatives, add regression fixtures, assert accuracy floors in `tests/golden`.
25. **Docs + status** — README, update this plan's status section, limitations list.

## 6. Test strategy

- **Unit** (pytest, fast, no I/O beyond temp PDFs): normalisation tables, quantity idioms,
  categorisation rules, word/line/column utilities, each parser on generated fixtures,
  relationship lookup/scope/anchors, fuzzy guard, ladder levels, assignment conflicts,
  quantity verdicts, check taxonomy, Excel structure, harness metric maths.
- **Fixtures**: rendered PDFs designed to break naive extraction (two columns, wrapped lines,
  repeated REF, ™, page break mid-table, zero-qty rows, expired rows, annotation redline).
  Every parser bug found later gets a fixture.
- **Integration**: `kaizen run datasets/golden` produces run.json + report.xlsx; sheets and
  columns asserted; `kaizen eval` produces metrics JSON.
- **Golden**: measured precision/recall must meet floors (set after tuning, targeted ≥ 0.95
  discrepancy precision and recall on the synthetic set; real values reported, never invented).

## 7. Dataset strategy

- 10 synthetic SKUs in one product family (`12951xx` style codes with `NS`/`FNS` suffixes), sharing
  a ~30-component kit catalog modelled on the PowerPICC example in the brief (BOM-style terse
  names vs label-style names).
- Each SKU seeds specific scenarios; `SCENARIOS.md` lists them. Coverage of the 14 required cases:
  exact, reordered wording, relationship match, qty mismatch, missing on label, extra label item,
  REF mismatch, ambiguous fuzzy, non-physical BOM rows, inactive BOM row, parenthetical qty,
  wrapped label line, multiple similar descriptions, fuzzy-must-not-accept.
- Ground truth is generated from the scenario definitions, not hand-typed, so it cannot drift.
- Two SKUs also ship an XLSX BOM export to exercise the table parser.
- Generated files are committed so the flow works from a clean checkout; `kaizen dataset build`
  regenerates them deterministically.

## 9. Risks

| Risk | Mitigation |
|---|---|
| Synthetic layouts diverge from real JDE/MasterControl output | Parsers keyed on header words and geometry, not absolute coordinates; swap in real files at checkpoint 1 and add as fixtures. |
| Threshold tuning overfits the synthetic set | Keep thresholds in config, report them, include adversarial cases; re-tune on real data. |
| Over-flagging | Categorisation + active-line filtering + idiom reasoning; eval tracks false positives explicitly. |
| Scope creep | P1/P2 items rejected until §8 passes. |
| Python 3.14 default on machine | `.venv` pinned to 3.13; `requires-python >= 3.12`. |

## 13. Forensic audit findings and resolutions (4 Sep 2026)

An independent audit (six perspectives: reviewer, quality engineer, auditor, developer, problem owner,
sceptical judge) found 12 verified issues. All were fixed test-first (`tests/unit/test_audit_fixes.py`).

| # | Severity | Finding | Resolution |
|---|---|---|---|
| 1 | HIGH | Old ↔ New ignored sub-quantity `(3 per)` and UOM changes → auto-cleared | Sub-quantity and UOM are part of the "unchanged" test; changes raise UNEXPECTED_LABEL_CHANGE. |
| 2 | HIGH | Fuzzy resemblance satisfied PCO expectations (`22G x 1.5in` vs `22G x 1in` cleared) | Only exact/relationship fits mark an expectation satisfied; fuzzy fits are POTENTIAL and need validation. Numeric guard now flags partially overlapping numbers (subset rule). SUBSTITUTE expectations get the outgoing item's wording from the BOM. |
| 3 | HIGH | PCO DELETE treated "never found" as applied (variant item number, skipped page) | Absent-by-number now checks inactive rows, look-alike descriptions under other numbers and skipped-page warnings; those cases are POTENTIAL with the evidence named. |
| 4 | HIGH | Row ids collided when a set held two labels/drawings/BOMs | Row ids carry a document-pair token (`R-<sku>-<pair>-<seq>`). |
| 5 | MEDIUM | Run id ignored parser/check versions | Parser and check versions are part of the run-id seed. |
| 6 | MEDIUM | Item on two operation sequences: only the first row was evaluated | Rows selected by operation sequence; without a sequence the row is POTENTIAL and lists the sequences. |
| 7 | MEDIUM | Keyword categorisation removed physical components (INSERT, INK, BOX) silently | Phrase-level patterns; every excluded BOM line is now an explicit `exempt` row with its reason. |
| 8 | MEDIUM | Item-anchored relationships ignored the BOM wording | Anchored pairs with unknown BOM wording are POTENTIAL ("not a known term — reviewer to confirm"). |
| 9 | MEDIUM | Duplicate BOM parents: last file silently won | Every BOM with the parent is evaluated; a coverage row flags the duplication. |
| 10 | MEDIUM | Shared SQLite connection across API threads; blind mode client-controlled | Writes serialised with a lock (concurrency test). Blind mode remains a query parameter for this single-machine prototype — documented gap. |
| 11 | LOW | `1,000.0000` became a MAJOR quantity mismatch | Thousands separators parsed everywhere quantities are read. |
| 12 | LOW | Exempt/header rows inflated auto-cleared counts and the business case | Effort counts use reviewable rows only (item and change roles). |

Suite after fixes: see §10 numbers updated in the completion report.
